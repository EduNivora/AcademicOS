# AcademicOS — Document and Attachment Viewer Architecture

## Scope

This document defines the Release 1 document path. AcademicOS stores course attachments in its local SQLite database. The viewer is a consumer of those records; it is not a backup, restore, synchronization, or export subsystem.

## File lifecycle

1. A student selects an attachment through the existing file picker.
2. The picker supplies bytes to the course-material flow. The application stores the bytes in the course_materials.file_bytes BLOB column and stores a dbblob:// marker in file_path.
3. Course-material list queries return metadata only. They deliberately omit file_bytes, so opening the course screen does not materialize every attachment in memory.
4. Only after the student opens an attachment does CourseMaterialFileService query the selected row's BLOB through getMaterialFileBytes.
5. The service validates the recorded extension, rejects empty or oversized content, and writes one private app-cache file. File names are generated by the app; user-provided path components are never used as a filesystem path.
6. PDF is opened in-app with pdfx from the app-owned cache file. The native document is closed before the cache file is deleted when the viewer route is disposed.
7. DOC, DOCX, PPT and PPTX are handed to Android/iOS through open_filex. The plugin uses the platform file-opening mechanism and FileProvider-style URI sharing; no broad storage permission is requested. A launched external app may read asynchronously, so the cache file is retained for up to seven days and stale files are swept on the next document preparation.
8. TXT remains a local, read-only text view. Unsupported types are rejected; they are never sent to the PDF renderer.

## PDF viewer

- The PDF engine is not initialized on unrelated screens. The viewer route is only constructed after an explicit open action.
- PdfDocument.openFile lets the native renderer read the app-cache file instead of copying the complete BLOB into a second Dart byte buffer.
- PdfViewPinch provides progressive page rendering and pinch zoom. The application adds page navigation, a current-page/page-count indicator, and bounded zoom controls.
- Document errors are converted into Arabic messages for missing, empty, corrupt, or unsupported files.
- The route owns the native document handle and temporary file lifecycle. Closing the route closes the native document and then deletes the file.
- A failed/cancelled open is handled without retaining a native document handle.

## Office handoff

The first release intentionally does not ship an Office rendering engine. The supported extensions are .doc, .docx, .ppt, and .pptx. open_filex maps them to platform MIME types and Android VIEW intents. The Android manifest exposes only the four corresponding MIME types through package-visibility queries; it does not request broad filesystem access. noAppToOpen, missing-file, and permission/error results are translated into a user-facing status.

The temporary file is app-owned and created under the application cache directory. The Android FileProvider path configuration is restricted to the edunivora_materials cache subdirectory. It is not deleted immediately after a successful intent handoff because Android may open it asynchronously. It is eligible for cleanup after seven days.

## Lazy loading and memory limits

- getAllMaterials and getMaterialsByCourseId are metadata-only queries.
- Attachment BLOB bytes are read for one material ID after a user action.
- The existing 50 MiB attachment ceiling is enforced again before writing a cache file.
- No PDF file is downloaded or fetched from a remote URL by the viewer.
- The viewer uses a file path; it does not keep a second full Uint8List copy alive for the lifetime of the route.
- PDF text extraction reads one page at a time and stops at 200,000 characters.

## Summary pipeline

Presentation and extraction are separate:

DocumentViewerScreen → DocumentSummaryService → PdfTextExtractionService → LocalSummarizerService

- Summary is only started when the student explicitly requests it.
- The extractor creates a separate temporary copy for flutter_pdf_text, reads page text lazily, and deletes the copy in a finally block.
- Extracted text is passed only to the existing local extractive summarizer. The PDF bytes and extracted text are not sent to Gemini, Cloudflare, Neon, or another network service.
- Image-only/scanned PDFs return noExtractableText. OCR is not claimed or silently attempted.
- Extraction errors do not produce a fabricated summary.

## Dependency decision

| Package | Decision | Reason |
|---|---|---|
| pdfx 2.11.0 | Adopt for in-app PDF | MIT licensed; Android uses the platform PdfRenderer; supports page count/navigation and pinch zoom; its minimum Flutter version is 3.29, compatible with the repository CI Flutter 3.41.8. |
| open_filex 5.0.0 | Adopt for Office handoff | Uses platform file-opening intents and typed outcomes including noAppToOpen; avoids an in-app Office rendering engine and broad file permissions. |
| offline_document_viewer 0.1.0 | Remove | Bundles a multi-format viewer that is unnecessary for the Release 1 PDF/Office split; its single early release and unclear licensing/maintenance evidence do not justify its footprint. |
| flutter_pdf_text 0.9.0 | Retain for local extraction | Provides page-by-page lazy text extraction on Android/iOS; use only on explicit summary action and with bounded file/text sizes. |

## Failure and recovery rules

- Missing BLOB: show an attachment-unavailable message; do not fall back to an untrusted path.
- Empty or oversized file: reject before writing a cache file.
- Invalid PDF header: reject before opening; the native parser remains the final corruption check.
- Corrupt or password-protected PDF: show a readable open/extraction error; do not treat it as an empty valid document.
- No compatible Office application: remove the unconsumed temporary file and tell the student no compatible app is installed.
- Successful Office handoff: retain the cache file for the seven-day safety window.
- Screen disposed during PDF loading: close any document that completes late and remove the viewer-owned cache file.
- Temporary cleanup failure: preserve the original SQLite BLOB and retry cleanup later.

## Test strategy

- Unit tests: BLOB-on-demand service, extension and size validation, safe cache paths, external-open outcomes, temporary-file cleanup, text extraction status mapping, and local summary separation.
- Widget tests: page counter, RTL controls, page-boundary behavior, and zoom/navigation callbacks.
- Android integration: native PdfRenderer open/page count, actual page-text extraction, in-app viewer lifecycle, cleanup, and Office VIEW-intent handoff.
- Existing Android SQLite integration remains in the same emulator gate.
